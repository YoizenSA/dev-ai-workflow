SOLO V2 · ywai profiles · demo de uso

Un comando por contexto:
ywai dev · ywai qa · ywai personal

Cada palabra es un runtime aislado de opencode2: su config, su DB, su servicio, su auth. No se mezclan. Esto no toca V1 y nunca toca ~/.config/opencode global. Abajo lo ves con gráficos y lo pruebas en la terminal simulada.

🧭 La idea en 10 segundos

ywai dev abre tu opencode2 de desarrollo. ywai qa abre otro totalmente separado para testear. ywai personal otro para tus cosas. Misma máquina, cero choques.

ywai dev→ perfil dev :4096
ywai qa→ perfil qa :4097
ywai personal→ perfil personal :4098
global V1→ ni se toca

1 · Cómo se usa (el flujo real)

Cuatro pasos. Del install al día a día. Cada tarjeta es un comando que puedes probar abajo en la terminal.

1

Crear perfiles

Una vez. --init copia solo tu config actual (agents, skills), nunca la DB ni el servicio.

ywai profile create dev --init ywai profile create qa ywai profile create personal
2

Abrir cada contexto

Atajo directo. Sin flags raros. Cada uno levanta su propio servicio en su puerto.

ywai dev ywai qa ywai personal
3

Mandar prompts sin abrir TUI

Para scripts y CI. Todo lo que va después se pasa a opencode2.

ywai qa "corre los tests" ywai dev -- run "refactor auth"
4

Ver y curar

Lista, detalle y doctor siempre scoweados al perfil. Nada global.

ywai profile list ywai profile show qa ywai profile doctor

2 · Gráfico: qué aísla cada perfil

En V2 el server es compartido por defecto y la DB se bloquea si se comparte (database is locked). Por eso cada perfil es un XDG home completo. Lo global queda intacto a la derecha.

Lee el gráfico así: cada columna de color es un mundo aparte (pueden correr en paralelo sin database is locked). La columna punteada roja es lo que nunca tocamos.

5 · Qué setea ywai dev (sin magia)

ywai dev → exec con env: XDG_CONFIG_HOME=~/.ywai/profiles/dev/config # opencode.jsonc, agents/, skills/, cli.json XDG_DATA_HOME=~/.ywai/profiles/dev/data # → …/data/opencode/opencode.db, log/, repos/ XDG_STATE_HOME=~/.ywai/profiles/dev/state # → service.json (¡un server por perfil!) XDG_CACHE_HOME=~/.ywai/profiles/dev/cache # bin/, descargas TMPDIR=~/.ywai/profiles/dev/tmp OPENCODE_DB=…/dev/data/opencode/opencode.db # evita database is locked # NO: HOME= (rompe git/ssh), OPENCODE_APPNAME (no anda en Linux), tocar ~/.config/opencode

6 · Cómo ywai mantiene cada perfil (sin que se pisen)

Cada perfil recibe el mismo pipeline de install, pero scoweado a su XDG. Nada es global: ni agentes, ni skills, ni MCP, ni plugins, ni doctor. Así un ywai update no rompe al resto.

A

Install scoweado

Agentes .md flat + permisos v2 + delegations + skills + MCP (engram, graft) + plugins v2, todo dentro del perfil.

ywai install --profile qa → …/qa/config/opencode/agents/ → …/qa/config/opencode/skills/ → mcp.servers en …/qa jsonc
B

Update sin contagio

Re-aplica solo al perfil pedido. Prunea huérfanos, saca MCP retirados, repara plugin Orca v2, deja el resto intacto.

ywai update --profile dev ✓ agents re-render ✓ retired MCPs removed ✓ lab, qa ni se tocan
C

Doctor por perfil

Mismo check, otro root. Detecta plugin V1, cli.json compartido, DB con lock, auth faltante.

ywai profile doctor qa [ok] service :4097 [warn] falta auth Go sub
D

Backup + prune

Antes de sobrescribir, snapshot a ~/.ywai/agent-backups. Lo que ya no está en el manifiesto se borra solo de ese perfil.

…/qa → backup .bak PruneUnlistedAgents(qa) RemoveStaleSkillLinks(qa)
qué vive DENTRO de cada perfil (ej: qa) — todo lo que ywai toca: …/qa/config/opencode/opencode.jsonc # model, default_agent, permissions[], mcp.servers{}, skills[] …/qa/config/opencode/agents/*.md # orchestrator, dev, qa… flat + sidecar .ywai-groups.json …/qa/config/opencode/commands/*.md # /review, /plan… por perfil …/qa/config/opencode/skills/ # + ~/.claude/skills compat, sin duplicar …/qa/config/opencode/cli.json # theme/keybinds TUI propios …/qa/config/opencode/service.json # server privado del perfil …/qa/data/opencode/opencode.db # sessions v2 solo de qa # Regla: ywai install/update/doctor siempre reciben --profile (default: todos, en serie, parando servicio antes de escribir).

En la terminal de arriba prueba: maintain qa para ver el pipeline simulado.

7 · Presets en install / update (ya vienen con agents + skills)

Al crear, elegís preset. Define grupos, skills, MCP, modelo, permisos y theme. Después lo tuneás por perfil o desde la web.

🛠

dev — full core

12 agentes core · skills TS/React · MCP graft+context7+engram · model sonnet · edit allow (no commit).

ywai env create dev --preset dev ywai install --profile dev
🧪

qa — estricto

core + qa-automation · skills tdd/testing/playwright · deny snapshot -u · model preciso.

ywai env create qa --preset qa ywai install --profile qa
🌱

personal — liviano

ask/dev/memory · skills mínimos · Ollama local · modelo barato · billing separado.

ywai env create personal --preset personal ywai install --profile personal
🧬

lab — clon, no preset

Clona dev para romper sin miedo. DB fresca, auth a revocar.

ywai env clone dev lab

8 · Desde la web también (mismo store, todo configurable)

Control UI :5768 → /envs. CRUD + preset picker + toggles + editores + estado. Lo que cambia en web lo ve el CLI y viceversa.

9 · Evals de cada profile (misma suite, mundos separados)

Corre la suite en cada servicio aislado y compara. Historial en <p>/evals/run-*.json. CLI + web.

En la terminal prueba eval qa o compare dev qa — funciona con cualquier par, ej. compare dev1 dev2 para decidir un cambio de modelo/preset.

Demo estática — nada toca tu máquina. Propuesta: ywai env en Go, solo v2, atajos ywai dev / qa / personal como subcomandos dinámicos.
