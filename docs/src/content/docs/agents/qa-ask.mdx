# QA Ask

El qa-ask responde preguntas de testing a testers manuales que entran a automatización: expertos en testing, principiantes en tooling — la pregunta siempre es sobre la herramienta, nunca sobre si entienden testing.

## Qué hace

1. **Concepto antes que sintaxis** — Siempre dice *por qué* existe la práctica: quien entiende por qué `data-testid` le gana a un selector CSS decide el próximo caso solo.
2. **Revisa memoria primero** — `mem_search` antes de explicar, para construir sobre una explicación anterior en vez de repetirla.
3. **Aterriza en tu stack** — Un snippet con el framework del repo vale más que uno genéricamente correcto.
4. **Enseña los 4 gotchas** — Sleeps fijos en vez de condiciones; tests acoplados a implementación que rompen en cada refactor; estado compartido order-dependiente; aserciones que nunca pueden fallar. Si la pregunta toca uno, lo nombra.
5. **Escala trabajo, no preguntas** — Devuelve a `@qa-orchestrator` lo que sea trabajo (una suite entera, multi-paso, estrategia); se queda con lo que una explicación o ejemplo corto resuelve.

## Cuándo usarlo

| Tarea | Ejemplo |
|---|---|
| Cómo testear algo | `@qa-ask ¿Cómo mockeo API calls en Vitest?` |
| Frameworks | `@qa-ask ¿Unit o integration para este caso?` |
| Mejores prácticas | `@qa-ask ¿Cómo testeo error handling?` |

## Routing

| Tarea | Handler |
|---|---|
| Escribir la suite | `@qa-dev` |
| Revisar tests existentes | `@qa-reviewer` |
| Explorar el repo para responder | `@finder` |

## Límites

| ✅ Puede | ❌ No puede |
|---|---|
| Responder y ejemplificar | Escribir tests completos (`@qa-dev`) |
| Explicar frameworks y patrones | Revisar código (`@qa-reviewer`) |
| Guiar paso a paso | Ejecutar cambios en el repo |

<Aside type="tip">
Para aprender testing guiado en vez de una respuesta puntual, el grupo QA Automation tiene flujo con `@qa-orchestrator`.
</Aside>
